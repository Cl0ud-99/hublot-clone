# hublot-clone

`hublot.darkroom.engineering` 的 WebGL2 + GLSL 复刻实验。

## 快速开始

```bash
pnpm install
pnpm dev
```

打开 http://localhost:5173 —— 需要浏览器支持 **WebGL2**。

## 对拍

所有参数与原站同名，可以用同样的 URL 直接对比：

```
?time=7.08&yaw=-18&pitch=0&row=11&hublot=1&cities=1&cirrus=0.5&turbulence=0.35
```

| URL 参数 | 含义 | 默认 |
|---|---|---|
| `time` | 巴黎时间（6.0–10.5） | 7.08 |
| `row` | 座位排数（1–28） | 11 |
| `hublot` | 是否显示舷窗（0/1） | 1 |
| `px` / `py` / `pd` | 相机位置微调（cm） | 10 / 0 / 25 |
| `yaw` / `pitch` | 视线角度（度） | -18 / 0 |
| `cities` | 城市灯光强度 | 1 |
| `lowClouds` / `cirrus` | 云量 | 0.3 / 0.5 |
| `turbulence` | 湍流 | 0.35 |
| `ev` | 曝光档位 | 0 |
| `cabin` | 舱内补光 | 0 |
| `sound` | 声音开关 | 1 |

### 大气：单次散射 + 多重散射

这是整个项目里物理含量最高、也最容易「看起来对但其实错」的部分。

#### 为什么必须做多重散射

单次散射只积了「太阳 → 散射点 → 相机」一条折线。太阳一旦落到地平线以下，
低层大气整片进入地球本影，单次散射几乎归零 —— 天空会在几分钟内从蓝变黑。
真实世界里高层大气（20~60 km）仍然被照亮，那里的光经过 2 次、3 次……
散射后落到眼睛里，这就是「蓝色时刻」。

在默认时刻 `time=7.08`（太阳高度 **-11.7°**，航海暮光）：
- 单次散射贡献的天顶辐亮度只有 **4.6e-5 / 9.6e-5 / 3.4e-4**（RGB）
- 多次散射贡献 **7.2e-6 / 2.0e-5 / 1.3e-4**
- 合计 **5.3e-5 / 1.2e-4 / 4.7e-4**

如果没有多次散射，这一帧的天顶亮度会低一个数量级，整片天空发黑。

#### 算法（Hillaire 2020 的各向同性近似）

记 `F_n(x)` 为「在 x 点、经过 n 次散射后到达的方向平均辐亮度」：

```
F_1(x) = (1/4π) ∫_Ω L_1(x, ω) dω                    ← 第一阶：带真实相位函数
F_n(x) = (1/4π) ∫_Ω ∫ T(x,x_t)·σ_s·F_{n-1}(x_t) dt dω   ← 高阶：各向同性
```

主着色器里把 `σ_s(x)·F_total(x)`（`F_total = ΣF_n`）当作各向同性内散射源加进
ray-march 即可 —— **注意不要乘太阳透射率**，LUT 里已经包含了完整路径的消光、
地球本影和所有阶数。

预计算只需要 6 个 32×32 的 GPU pass（5 阶 + 1 次求和），
实测 **3.3 ms**（含 `readPixels` 同步），完全是一次性成本。

LUT 只对 `(海拔 h, 太阳天顶角余弦 cosZ)` 两个维度建表 —— 因为大气球对称，
绕本地垂线旋转后「周围的散射光平均值」与方位角无关。

海拔用平方映射 `h = 100·u²`：0~10 km 集中了 70% 的大气质量，
均匀采样会让这段只有 3 个 texel，太粗。

#### 太阳方位：相对舷窗定义，不是地理方位

原站 bundle 里：

```js
const _ = az - Math.PI;                    // ySe = 180°
sunDir = (cos(_)*cos(el), sin(el), sin(_)*cos(el));
```

太阳方向直接写在着色器世界的相机坐标系里，`-Z` 就是 `yaw = 0` 的视线方向。
效果是 **日出永远发生在舷窗正前方**，默认 `yaw = -18°` 把它推到画面右侧。

早期版本把太阳放在真实地理坐标系里，默认视角恰好背对太阳 123° ——
反日点的暮光辐亮度只有 5e-5，再怎么调物理模型都是一片黑。
这不是大气模型的问题，是「太阳根本没在你的窗外」。

日期也是写死的第 298 天（10 月 25 日），不跟随系统日期 ——
否则同一时刻在 6 月和 10 月能差 40° 太阳高度，默认观感完全不可复现。

#### 相机自动曝光

从正午到暮光，天空辐亮度跨 5 个数量级（1e-1 → 1e-8）。
固定曝光不可能同时照顾两头：要么白天死白，要么暮光全黑。

`autoExposureEV()` 按太阳高度给出一条分段曲线：

| 太阳高度 | +12° | 0° | -3° | -6° | -12° | -18° |
|---|---|---|---|---|---|---|
| EV | 0 | 0.6 | 0.6 | 3.5 | 9.0 | 9.0（上限） |

`-3°` 到 `0°` 这一段刻意压平：日出瞬间地平线辐亮度变化极快，
曝光跟着线性追会让画面「呼吸」。压平相当于相机锁死曝光，让太阳自己提亮画面。

配套的三件事必须一起做，否则会翻车（都踩过）：

1. **舱内灯光 ÷ `exposure^1.15`** —— 否则暮光档位内壁直接爆白
2. **城市灯光 ÷ `exposure^1.55`，星星 ÷ `exposure^0.95`** —— 同理，点光源必须反向缩放
3. **bloom 阈值按「显示亮度」而不是「场景辐亮度」** —— 见踩坑记录


### 飞行运动

`uFlightOffset` 驱动地表、低云、城市灯光、卷云的图案流过画面。

- 速度 **0.21 km/s**（约 756 km/h，REV 原站同值）
- 关键设计：**偏移采样坐标，而不是移动相机**。
  移动相机会让地平线和球面求交结果抖动；
  偏移采样坐标只让图案流动，几何完全稳定。
- 各层速度不同：地面 1.0×、低云 0.85×、卷云 0.72×
  （不同高度层风速不同，这个差异本身也是真实感的来源）

实测：3 秒内地面区域平均像素差 17.95、17.3% 区域显著变化。

### 机翼表面细节

| 细节 | 实现方式 |
|---|---|
| 面板分割线 | 程序化 Canvas 纹理（1024×2048），贴在 UV 上 |
| 凹缝立体感 | 暗线 + 一侧亮边（见下） |
| 蒙皮色差 | 纹理里的大范围低透明度色块 |
| 扰流板轮廓 | 纹理里的矩形描边 |
| 前缘防冰带 | 纹理左侧的渐变暗带 |
| 襟翼滑轨整流罩 | 3 个缩放球体，纺锤形，挂在后缘下方 |

UV 约定：`u` = 弦向（0 前缘 → 1 后缘），`v` = 展向（0 翼根 → 1 翼尖）。
弦向面板线会随翼型收缩自然收敛 —— 真实机翼就是这样。

#### 为什么面板线要画成「暗缝 + 亮边」

只画一条黑线会让机翼看起来像用马克笔描过边，是典型的「卡通化」翻车。
真实蒙皮缝隙是一个**凹陷**：缝底在阴影里（暗），而缝隙的一侧边缘
会因为受光而略亮。这个「暗-亮」配对才是人眼识别
「这是凹槽而不是画上去的线」的依据。

参数记录（两轮调优）：
- 第一轮：主缝 13px / alpha 0.42 → 画面上几乎看不见（被各向异性糊掉）
- 第二轮：主缝 15px / alpha 0.68 + 亮边 → 纹理最深暗谷 114 → 51（深度 +45%），画面上可读

### 已知差距（下一步）

1. ~~**暮光是经验模型**~~ → **已解决**：改成 5 阶多重散射 LUT，
   与双精度 CPU 参考对拍误差 0.38%（见上文「大气」章节）。
2. **面板线在舷窗视角下偏淡**。机翼在这个角度被极度压缩，
   细节能看出但不够醒目 —— 物理上正确，但可以继续加对比。
3. **卷云只覆盖仰角 5.7° 以上**。地平线附近的卷云被淡出掉了
   （否则掠射拉伸会产生竖向拖尾），真实情况下那一段会被下层大气遮住，
   所以观感上没问题，但严格说少了一点云。
4. **爆光度曲线是「半个物理 + 半个摄影」**。真实相机不会把 -12° 的
   天光提亮 500 倍还保持同样的信噪比；这条曲线是为了「每个时刻都好看」
   调的，不是照相机仿真。要更硬核应该做直方图自动曝光 + 时间适应。
5. **Mie 消光我们用了物理值**（散射 + 吸收 = `0.003996 + 0.00444`），
   而原站 bundle 里只写了 `n * 0.00444`（少了一半）。
   原站那处大概率是笔误 —— 我们在这一点上**故意不跟随**，
   因为跟随会让地平线雾霾过薄、日落偏亮偏黄。其余常数全部按原站。

### 卷云采样频率（重要）

`CIRRUS_KM_TO_UV = 0.05` 这个系数决定了卷云的颗粒度，不能随便改：

- 噪声纹理基频是 **4 周期/UV**
- 视野内卷云平面坐标 `p2` 约跨越 5~40 km
- 要让基频走 2~3 个周期，UV 跨度需要 0.5~0.75 → 系数 ≈ 0.05

早期用的是 `0.004`（UV 跨度仅 0.02），基频完全没变化，
画面里只剩 64/256 周期的高频通道在混叠 —— 这就是顶部「梳齿状横条」的根因。

**淡出区间必须完全覆盖 dirUp 钳制区间**，否则重叠区里平面被钳住、
UV 不再随角度变化，云会被拉成一根根竖向拖尾，而淡出系数还没归零，
这些拖尾就会露出来（比横条更难看）。

## 开发踩坑记录

这些是在 Windows + WebGL2 环境下实测踩到的，记下来能省很多时间：

0. **「经验项」在低动态范围下看不出来，一进 HDR + 自动曝光就炸**。
   本次改造暮光时，一次性揪出四个同类的历史遗留：

   | 位置 | 原写法 | 症状 |
   |---|---|---|
   | `sunIrradiance()` | 按太阳高度做经验红化 + -8° 熄灯 | 同一份消光被算两次；暮光全靠手工 tint |
   | `sky.frag` 日晕 | `pow(c,16)*0.08` 常数项 | 离太阳 19° 还有 2.7 的线性亮度，半个窗口死白 |
   | `sky.frag` 地面雾 | `uSunColor * 0.0009 * (1-viewTrans)` | 与物理散射重复，曝光 512× 时整块地面纯白 |
   | `sky.frag` 卷云 | `uSunColor * (0.05 + 0.03*sunFacing)` | 与太阳高度无关的常数，夜里云比天还亮 |

   共同特征：**写死一个「看起来差不多」的常数，乘上 `uSunColor`**。
   曝光 = 1 的年代它们只是「稍微亮一点」，自动曝光一上就变成几万倍的错误。
   教训：凡是乘了 `uSunColor` 的项，必须问一句「太阳落山后它应该归零吗？」

0. **bloom 的曝光被乘了两次**。
   `bloom-bright.frag` 里 `c = texture * uExposure`（阈值要按显示亮度比较），
   `composite.frag` 又 `color *= uExposure` —— 于是 bloom 变成 `exposure²`。
   曝光 = 1 时 1² = 1，完全看不出来；自动曝光 512× 时是 26 万倍，
   整个窗口被 bloom 糊成一片白光。**这是只会在 HDR 曝光变化后才暴露的 bug。**

0. **半精度浮点 RT 的 `readRenderTargetPixels` 会骗人**。
   用 `Float32Array` 去读 `HalfFloatType` 的 RT，WebGL 抛 `INVALID_OPERATION`，
   buffer 原样返回 —— 全是 0。于是 LUT「看起来全零」，其实 GPU 算得好好的。
   解法：调试阶段直接用 `FloatType`（32×32×RGBA32F 只有 16 KB），
   或者读的时候传 `Uint16Array` 自己解 half。

0. **臭氧吸收的蓝通道差一个零**。
   原站 bundle：`V5(.00277,.001881,26e-5)` → `[0.00277, 0.001881, 0.00026]`。
   我们写成了 `0.0026`，蓝通道吸收放大 10 倍。
   后果：任何长光程（地平线、暮光）蓝光被吃光，天空从蓝渐变变成**黄绿色**。
   这个常数的量级错误比它的绝对值影响大得多。

0. **`east = north × up` 是西，不是东**。
   在赤道本初子午线上验证：`north=(0,1,0), up=(1,0,0)`，
   `north × up = (0,0,-1)`，而东应该是 `+z`。正确写法是 `up × north`。
   因为机舱和相机都建在同一套错坐标里，画面自洽，所以一直没暴露；
   一旦把太阳和真实方位对齐就会立刻出错。

0. **掠射表面上的纹理必须开最大各向异性过滤**。
   机翼面板线纹理「明明画对了、UV 也对、map 也挂上了，但画面上什么都看不见」，
   原因就是各向异性不足：
   - 机翼在舷窗视角下弦向 ≈ 1.7 纹素/像素，展向 ≈ 13 纹素/像素
   - 比例约 8:1，而 `anisotropy = 4` 扛不住
   - GPU 只能按最差方向选 mip（≈ 3.7 级），把清晰方向的面板线一起糊掉
   解法：`tex.anisotropy = renderer.capabilities.getMaxAnisotropy()`（通常 16）。

   排查这类问题的高效手段：把 map 换成**红白粗条纹**，
   如果条纹不出现，说明贴图没被采样（而不是纹理内容问题）。

0. **舷窗视角的坐标约定，一开始就必须定死**（本次最大的返工来源）。
   坐在机身侧面、视线垂直于机身轴线，意味着：

   | 方向 | 应该是 |
   |---|---|
   | 视线（舷窗外） | -Z |
   | 机身 / 飞行方向 | **X（屏幕横向）** |
   | 机翼展向 | **-Z（伸向远方）** |
   | 地面流动方向 | **横向（X）** |

   我最初把「飞行方向」和「机翼展向」都当成了 Z，结果：
   - 地面是**纵向**涌向镜头（像垂直下坠，不像侧窗）
   - 机翼**横在窗前**，看到的是翼型侧剖面（一条横刀）
   - 发动机短舱正对着镜头

   正确做法是把机翼组绕 Y 轴转 90°，让翼展从 +X 转到 -Z。
   转完之后才能看到**翼面**，透视收缩也才对。

0. **3D 几何「看不见」时，别靠改参数猜，直接投影到 NDC 看坐标**。
   本次机翼消失了 4 次，每次原因都不同：
   ① 尺寸过大跑出视锥 ② 位置偏右落在窗洞外
   ③ 过曝成白色 ④ 金属度过高在暗环境变全黑。
   靠肉眼调参数会陷入无限试错。正确做法是加一个开发期钩子
   （`window.__hublot = { renderer, scene, cabin, rig }`），然后：
   ```js
   // 顶点投影到 NDC，-1~1 之外就是不在屏幕上
   const nx = (cx * f / aspect) / -cz;
   const ny = (cy * f) / -cz;
   ```
   再配合看包围盒、算相机空间 z。
   **杀手锏：把目标物体改成纯自发光红色 + 隐藏遮挡物**，
   一次就能区分「不可见」和「被遮挡」——本次就是靠这招发现
   机翼其实好好的，只是整个跑到了窗洞右侧外面。

0. **卷云的采样平面高度不能离相机太近**。
   卷云层设在 11 km、相机在 10.4 km —— 只高 0.6 km。
   视线向上 45° 时云层距离只有 0.85 km，采样到的水平范围不到 1 km，
   整片云被放大成几乎恒定的色块，**任何流动都看不出来**。
   要看到纤维结构，云层需要高出相机数公里（本项目用 14 km）。

0. **但抬高云层会引入地平线附近的摩尔纹**。
   `tCi = (云高 - 相机高) / dot(dir, up)` 在视线接近地平线时
   `dirUp → 0`，tCi 暴涨到几百公里，采样坐标在相邻像素间跳变巨大
   → 出现密集横向条纹。三重防护：
   给 `dirUp` 下限、限制 `tCi` 上限、用地平线附近的 smoothstep 淡出
   （真实大气里地平线附近本来也看不到高层卷云）。

0. **各向异性拉伸做卷云会得到「扫描线」**。
   用 `p * vec2(0.35, 1.4)` 拉 4 倍想做纤维条，结果是非常规则的平行横条。
   真实卷云需要：低频噪声控制走向、域扭曲让纤维弯曲、
   脊线噪声只做细节（强度要压低），以及柔和的边缘过渡。

0. **内壁尺寸必须能覆盖超宽屏**（21:9 / 32:9）。
   舷窗内壁是有限大的几何体，而视野的水平张角随宽高比增大：
   `水平半张角 = atan(tan(fov/2) * aspect)`，32:9 下可达 ~72°。
   固定 4.8 m 宽的面板在超宽屏上会**露出天空**（左边一片黑或直接透出大气）。
   解法：按最坏情况动态算宽度 ——
   `(座位最大横移 + EYE_TO_WALL * tan(72°) + 安全边距) * 2`，
   并且窗洞数量要跟着面板宽度走，否则加宽出来的部分会变成
   一整片没有窗的实心壁面。

0. **`AmbientLight` 做不出内壁的明暗梯度**。
   它是各向同性的，只会把内壁整体提亮成一块均匀的深灰，看起来像塑料板。
   真实机舱里靠近窗洞的墙面被窗外光强烈照亮、越远越暗。
   用一个放在窗外的 `PointLight`（带衰减）就能得到这个梯度，
   成本极低但质感差别很大。

0. **上采样时绝不能「读 mips[i] 又写 mips[i]」**。
   WebGL 会报 `Feedback loop formed between Framebuffer and active Texture`
   并**静默拒绝执行 draw call** —— 表现为 bloom 完全不出效果，
   但控制台只有 warning 没有 error，极难发现。
   正确做法是加一组独立的 `upsampled[]` 做 ping-pong：
   读 `upsampled[i+1]`（更模糊），写 `upsampled[i]`。

0. **bloom 阈值必须跟场景的亮度尺度匹配，且随昼夜自适应**。
   这是本项目最隐蔽的一个坑：白天场景的线性辐亮度能到 5~20，
   而黎明前只有 0.02~0.3。阈值固定 0.85 时，
   夜景里没有任何像素能越过阈值 → bloom 静默失效，同样不报错。
   解法：`threshold = mix(0.06, 1.2, dayness)`。
   排查手段：加 `?debugBloom=1` 把 bloom 缓冲直接画到屏幕上，
   一眼就能看出是「缓冲空的」还是「合成没叠上去」。

0. **做 HDR + bloom 时，渲染进 RT 必须临时关掉 tone mapping**。
   机舱用的 `MeshStandardMaterial` 会被 three 自动注入
   `tonemapping_fragment`。如果渲染到 HDR 缓冲时还开着 ACES，
   机舱会被压缩两次、天空只压缩一次，观感撕裂。
   正确做法：`renderer.toneMapping = NoToneMapping` 渲染进 RT，
   色调映射只在最后的 composite pass 里做一次。

0. **bloom 必须在色调映射之前**。
   顺序错了（先 ACES + sRGB 再提取高光）会让光晕发灰、没层次，
   因为高光已经被压进 0~1 区间，没有动态范围可用了。

0. **相机宽高比必须在 resize 里更新**（最容易漏、症状最迷惑）。
   `PerspectiveCamera.aspect` 默认是 **1**，忘了赋值就会按 1:1 算投影矩阵，
   机舱几何被横向拉伸（1400×900 视口会拉宽 1.56 倍，竖长的舷窗变成横宽）。
   典型症状是「**天空正常、机舱拉伸**」的割裂感 —— 因为天空走的是全屏
   着色器里的 `uResolution`，自己算 aspect，不受相机影响。
   修复就是在 `resize()` 里加两行：
   ```ts
   camera.aspect = w / h;
   camera.updateProjectionMatrix();
   ```

0.5 **别把 Playwright 无头窗口里的低帧率当成性能问题**。
   实测过：空的 `requestAnimationFrame` 循环在该环境下也只有 1.3 fps，
   而同一个页面的 `setTimeout` 能跑 208 fps，GPU 的 `gl.finish()` 耗时 < 0.1 ms。
   窗口没有真正合成时，rAF 会被节流。判断性能要看
   「空 rAF 循环的上限」，而不是页面显示的 fps。

1. **`vite-plugin-glsl` 1.6.x 的默认导出是 `async function`**。
   直接放进 `plugins` 数组会得到一个未 await 的 Promise，
   插件静默失效（shader 被当作文本资源导出，页面白屏）。必须在
   `defineConfig(async () => { const p = await glsl({...}) })` 里 await。

2. **不要把该插件的 `watch` 设为 `true`**。它会在 `src/shaders/` 下创建
   `.tmpdir` 临时文件，Vite 的文件监视器随后去 watch 它，
   在 Windows 上抛 `EBUSY` 直接让 dev server 崩溃。

3. **three 的 `ShaderMaterial` 走 GLSL ES 1.00，不是 GLSL3**。
   所以 `textureGrad` 不存在，`texture2DLodEXT` 需要扩展，
   `dFdx/dFdy` 需要 `GL_OES_standard_derivatives`。
   本项目改为「解析计算相邻像素方向」+「多 tap 模糊」，零扩展依赖。

4. **不要手动声明 `attribute vec3 position`**。three 会自动注入内置属性，
   手动声明会触发 `'position' : redefinition` 编译错误。

5. **原生 `ShaderMaterial` 不会自动做色调映射和 sRGB 编码**。
   必须手写整套（曝光 → ACES → sRGB），否则画面会明显偏暗。
   同时要让 `renderer.toneMapping` 与手写的那套保持一致，
   否则天空和机舱的观感会撕裂。

6. **太阳辐照度的绝对尺度决定了整幅画面的曝光**。
   实测在 `(1.7, 1.85, 2.03) × 8` 附近最合适；用原站那种 ×50 的量级
   会让地面算到 3.4，ACES 之后直接死白。

7. **机舱不能挂在相机下**。否则转头时窗框会跟着转、永远贴在屏幕同一位置。
   正确做法是用「参考姿态」（yaw=0/pitch=0 时的相机朝向）来摆放机舱。
